jsonx / tutorial

Learn jsonx in twelve steps

jsonx draws JSON into your page with plain HTML templates. Your server answers with the data for a part of the page, a template turns it into HTML, and only what changed is updated.

Every step below has three parts:

  • The code. It's copied from this page's own source, so it's exactly what runs.
  • The result. It's live, so click and type in it.
  • The data. Each request appears here as it happens: what was sent, and the JSON that came back. That JSON is called the view.

The server is a pretend one in mock-api.js, running in your browser. Reload the page to start again. With Outline regions on, every region (see step 4) has a dashed border.

To use jsonx on your own page, load one file:

<script type="module" src="jsonx.js"></script>

1. Draw JSON with a template

We start with everything written out: an element to draw into, a URL to load, and a template, each named by id. Later steps show the shortcuts.

What happens

    
    
      
  1. When the page opens, jsonx finds jx-get on the div. You can't click a div, so it loads straight away.
    2. 
      
  2. The server answers with JSON. Look at it in the data panel.
    3. 
      
  3. jx-template="#greeting-template" says which template draws it. The answer is drawn into the element itself, replacing "Loading…".
    4. 
    


    
The rules for values

    
    
      
  • {{name}} prints the name field of the view.
    • 
      
  • A dot reaches inside an object: {{inbox.unread}} is 3.
    • 
      
  • Values are always printed as text, never as HTML. The motto contains <b> tags, and they show up as text. Anything a user typed is safe to print.
    • 
      
  • A name the view doesn't have prints nothing. It isn't an error.
    • 
    

    
The <template> tag is standard HTML. The browser keeps its contents hidden and inactive, so the template never shows on the page by itself.

When requests run

    
Each element has a natural moment, called its trigger:

    

      
ElementRuns on

      
<button>, <a>, and button components like <wa-button>click

      
<input>, <select>, <textarea>, and form componentschange

      
<form>submit

      
anything else (<div>, <ul>, …)load: right away

    

    
To choose a different trigger, use jx-trigger. For example, jx-trigger="input delay:300ms" waits until someone stops typing for 300ms, and jx-trigger="keydown[key=Enter]" runs when Enter is pressed.

    
Every click draws the whole template again with the new view. That doesn't mean rebuilding the HTML: jsonx only changes the text that's different.

  


  
  

    
3. Sending values

    
A control's name becomes a key in the request. jx-include picks which controls to send, by CSS selector.


    

      

      

        

          
          
          

          
          

          


          
          
        

        
Data
Type a name and click…

      

    


    
    
      
  • jx-post, jx-put and jx-patch send the values as a JSON body. jx-get and jx-delete put them in the URL, as ?name=Ada.
    • 
      
  • jx-vals adds fixed values, written as JSON. They win over controls with the same name, so "In French" always sends "fr".
    • 
      
  • A name with dots builds nested JSON: name="user.email" sends {"user": {"email": …}}.
    • 
    

    
That works, but notice how much we're repeating: two buttons each name the same target, the same template and the same inputs. The next step removes all of it.

  


  
  

    
4. Regions: the template inside

    
Put the <template> inside the element, and the element becomes a region. This is how most jsonx pages are written.

What a region means

    
    
      
  1. It draws itself. The template inside is its template. Its own jx-get loads when the page opens, just like step 1.
    2. 
      
  2. Buttons inside it redraw it. A button with no jx-target draws its answer into its region, with the region's template. So the server answers every button with the region's whole view, here {"count": 3}.
    3. 
      
  3. Its controls go with every request. That's the next step.
    4. 
    

    
A button's region is the nearest element around it that has a template. It works like closest() in JavaScript.


    
The same thing, written out

    
The region above is a shortcut for this explicit version. Both work, and they behave the same.

    
    
An element with jx-template="#id" is a region too. The only difference is where the template lives. Use an id when several places share one template, and the inside version for everything else.


    
Two more ways to write a region

    
A region with nothing to load, like a sign-in form, uses jx-region instead of a URL. It draws its template once with an empty view, {}. Step 9 uses one.

    
If you don't need a wrapper element, put the request on the template itself. Step 10 uses one.

    
  


  
  

    
5. Region values: every control, every request

    
Any request from inside a region sends every named control in the region, the way a form does. You don't list them with jx-include.


    

      

      

        

          
          

            
          

          
        

        
Data
Waiting for a request…

      

    


    
Change any box and look at Sent in the data panel. All four values go every time, so the server can work out the whole answer from one request.

    
    
      
  • Inputs as triggers. The inputs have jx-post too. Their trigger is change, so leaving a box after typing sends the request.
    • 
      
  • Values come back. value="{{bill}}" puts the server's value into the box. If the server corrects something (try 0 people), the box shows the correction. When an attribute is exactly one {{name}} and the element has a property with that name, like value or checked, jsonx sets the live property. So the box always matches the view.
    • 
      
  • Hidden inputs remember things. currency isn't on screen, but it's sent with every request, so changing the bill keeps your currency. The currency buttons override it with jx-vals, and the next view stores the new one.
    • 
    

    
That's the pattern for state like a selected tab, a filter or a page number: the server puts it in the view, a hidden input holds it, and every request sends it back. The page itself remembers nothing.

  


  
  

    
6. Lists, and where names are looked up

    
<jx-each items="items"> draws what's inside it once for each item in the list.


    

      

      

        

          
          

            
          

          
        

        
Data
Waiting for a request…

      

    


    
Where names are looked up

    
Inside <jx-each>, a name is looked up in the current item first, then outwards in the view around it:

    
    
    
      
  • {{name}}, {{qty}} and {{id}} come from the item.
    • 
      
  • {{store}} isn't on the item, so it's found on the view outside.
    • 
      
  • {{.}} is the item itself, for lists of plain strings like tags.
    • 
      
  • If an item had its own store field, that would win. Choose distinct names when that could be confusing.
    • 
    


    
Good to know

    
    
      
  • Values work in URLs too: jx-post="/api/list/{{id}}/toggle" gives each row its own address.
    • 
      
  • class:done="{{done}}" turns the class done on or off.
    • 
      
  • Items with an id are tracked by it. Removing one row removes just that row's elements, and the others stay as they are, even mid-typing.
    • 
      
  • <jx-each> isn't put on the page, so ul > li still matches in your CSS.
    • 
      
  • Adding sends item, the region's only named control. The server answers with draft: "", which empties the box.
    • 
    

  


  
  

    
7. Conditions

    
<jx-if> draws what's inside only when a value is there. <jx-else-if> and <jx-else> can follow it.


    

      

      

        

          
          

            
          

          
        

        
Data
Waiting for a request…

      

    


    
    
      
  • test="shipped" passes when the value is there. Missing, null, false, 0, "" and an empty list [] all count as "not there".
    • 
      
  • test="!notes" is the opposite. Here it's the empty-list message.
    • 
      
  • In a chain, the first branch that passes is drawn, and <jx-else> catches the rest. Only spaces and comments may sit between the branches.
    • 
      
  • There are no comparisons like step > 1, on purpose. The server sends a ready answer, like shipped: true. Logic lives in one place, and templates stay easy to read.
    • 
    

    
Tables and selects: the browser moves unknown tags out of <table> and <select> before jsonx sees them. In those two places, put the logic on the element: <tr jx-each="rows">, <option jx-if="x">, and jx-else-if / jx-else on the elements that follow.

  


  
  

    
8. Regions inside regions

    
A region's template can hold another region. Each one is its own little world: its own URL, its own view, its own buttons and its own controls.

Try each button, and watch the two clocks and the data panel.

    

      
Outer region #postInner region #comments

      
Loads from/api/post/api/post/comments, once the outer one has drawn it

      
Its view{title, likes, drawnAt}{comments, count, loadedAt, draft}

      
Its namesonly the outer view'sonly its own view's: {{title}} in here would print nothing

      
Buttons inside redrawthe outer regionthe inner region

      
Requests sendthe outer region's controlsthe inner region's controls (text)

    


    
The rules

    
    
      
  1. Each region's names come only from its own view. Views don't flow from an outer region into an inner one. If the comments need the post's title, the comments view includes it. (Inside one template, <jx-each> looks outwards as in step 6. That lookup stops at the region's edge.)
    2. 
      
  2. A button belongs to its nearest region. "Comment" redraws only the comments, and sends only text.
    3. 
      
  3. Redrawing the outer region leaves the inner one alone. Click "Like": the post's clock changes, but the comments' clock doesn't, and a half-typed comment stays. jsonx only updates the outer view's values, and the inner region is not one of them.
    4. 
      
  4. Reach across on purpose. jx-target="#post" sends the answer to another region, drawn with that region's template. jx-refresh="#comments" reloads another region once a request works, from wherever it last loaded.
    5. 
    

    
If an outer redraw removes an inner region, for example inside a <jx-if> that turns off, and later draws it again, it's a new region. It loads again from scratch.

    
Use nested regions when part of a page changes on its own, like comments under an article, or a live counter in a header. Each part then asks the server only for its own view.
  


  
  

    
9. Errors

    
When a request fails and the server explains why in JSON, jsonx redraws the region with its last view plus the error. You show it with ordinary template code.


    

      

      

        

          
          

            
          

          
        

        
Data
Click "Sign up" with the boxes empty…

      

    


    
The server answers with status 422 and {"errors": {"email": ["can't be blank"]}}. jsonx adds three names to the last view for the redraw:

    

      
NameWhat it holds

      
errorOne message for the whole thing: the server's error or message, or the errors joined together.

      
errorsA list for <jx-each>: [{field, message, text}].

      
fieldErrorsThe same by field, to show next to each input: {{fieldErrors.email}}.

    

    
    
      
  • What you typed stays in the boxes, so you only fix what's wrong.
    • 
      
  • The next successful answer replaces the view, so the errors disappear by themselves.
    • 
      
  • jx-region is a region with no URL (see step 4). It draws the form once with an empty view.
    • 
    

    
Step 8's comment box works the same way: post an empty comment to see its error.

11. Functions and shared data (optional)

    
So far every view came from a server. Two optional features let the browser supply views too: a function in place of a URL, and regions bound to shared data. Use them for state that never touches a server, or to reshape an API you don't control.


    

      

      

        

          
          

          
Basket: 


          

            
          


          

            
          

          
        

        
Data
Waiting…

      

    


    
Functions: fn:name

    
    
      
  • Anywhere a URL goes, fn:products calls the function products instead. It gets the same values a request would send (the region's controls and jx-vals), and returns the view, or a promise of one.
    • 
      
  • So templates don't care where a view comes from. A region can start on a function and later point at a real URL.
    • 
      
  • To fail, throw an error answer like { error: "…" } or { errors: {…} }. It's shown like a server's error from step 9. Try adding a fourth tea.
    • 
      
  • Returning nothing means there's nothing to draw here, like empty().
    • 
      
  • A function can call real APIs and reshape what they return, so you can adapt an API you don't control.
    • 
    


    
Shared data: jx-data

    
    
      
  • jx-data="cart" makes a region that draws the variable cart. Both the basket count and the basket list use it.
    • 
      
  • After any fn: call, every jx-data region is drawn again from its variable. So add() just changes cart, and empty() just replaces it. Regions whose data didn't change are skipped.
    • 
      
  • With big lists on the page, say what a button changes: <button jx-post="fn:add" jx-data="cart"> redraws only the cart regions, instead of checking them all.
    • 
      
  • This is how two distant parts of a page stay in step without jx-refresh.
    • 
      
  • Changing the data from other code, like a timer? Call jsonx.update() to redraw.
    • 
      
  • Use a plain <script>, as above, not a module: jsonx finds functions and variables by name, and a module's are private. In a module, put them on jsonx.functions and jsonx.data instead.
    • 
    

    
These put logic in the browser, which jsonx otherwise avoids. Server views stay the default. Reach for these for local state, and for APIs you can't change.

  


  
  

    
12. Components

    
A template can define a real web component. Give it a tag name and the props it takes, and use it like any HTML element. It renders with the same template language.


    

      

      

        

          
          

          

            
          

          
        

        
Data
Waiting for a request…

      

    


    
    
      
  • <template jx-component="vote-button" props="label votes"> defines <vote-button>. Each prop can be set as an attribute (label="Tabs"; favoritesCount would be favorites-count) or as a property. A {{value}} in a jsonx template sets the property, so you can pass objects and lists too.
    • 
      
  • It draws into its own shadow DOM, so its <style> only affects the component, and <slot> works.
    • 
      
  • Components fire events; pages decide. jx-emit="vote" fires a vote event when clicked, with the current item as event.detail. The component doesn't know what a vote does. Here, the page puts the request on the component itself, with jx-trigger="vote". The answer redraws the page's region as usual.
    • 
      
  • Put components in .jx files and pull them in with <template src="vote-button.jx"></template> to share them between pages. Conduit's <article-preview> is shared by both versions of the app.
    • 
      
  • Each one is a genuine Lit element (a LitElement). Other code can set its properties, listen to its events, and use it in React, Vue or Lit apps, as long as jsonx is on the page.
    •

<jx-else-if test="y">, <jx-else>The rest of the chain

      
value="{{draft}}"Exactly one value: sets the live property if there is one

      
class:done="{{done}}"Toggle a class

      
<template jx-use="#id">Draw another template here
